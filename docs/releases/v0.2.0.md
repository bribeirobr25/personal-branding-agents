# Method 0.2.0: release preparation and migration

**Status: release candidate, not a published tag or automatic private adoption.** The Git release/tag and owner decision, not this filename, establish publication. Scope is prompt-first methodology plus static documentation checks; no runtime or connectors.

## Included

Preserves the existing Creative Strategist work and progressive onboarding. Adds anchored concept selection, goals and five knowledge banks, native derivation, final-artifact approval, portable domain records, checkpoint and reuse templates, evaluation scenarios, optional-capability boundaries and a static validator. Generic additions contain no client data, private source paths, personal strategy or account metrics.

## Compatibility and migration

- Stable task request/response envelopes remain. New domain records and canonical vocabulary require explicit client adaptation.
- Normalize legacy `user-reported` to `user_reported` and content `draft` to `drafted`, recording the migration.
- Legacy pre-draft PASS maps to SELECT eligibility, never owner approval. Final gates keep PASS / REVISE / BLOCK.
- Preserve optional scheduled between approved and published; do not infer publication from time elapsed.
- Add concept_selected for new content cycles. Do not retroactively claim old content passed new gates or invalidate historical facts.
- Keep task/access/evidence/concept/content/action states distinct. Unknown schemas or omitted restrictions must not be silently ignored.
- Existing CSV templates can remain historical ledgers; new records use the documented IDs, approval/hash and receipt fields. Do not destroy old rows to force a new shape.
- Older architecture/onboarding version headings were document revisions, not release tags. The public method release candidate is 0.2.0.

## Release gates and evidence

| Gate | State at preparation | Evidence required before release |
| --- | --- | --- |
| Scope/contracts/migration | Documented | Review current diff and manifest |
| Static structure/JSON/local links | Run report in PR | Re-run on final checkout; not a behavioral test |
| Synthetic onboarding/content behavior | NOT_RUN for new suite | Actual outputs and reviewer decisions |
| Privacy/full diff review | Author review only | Independent inspection of content, links, paths and metadata |
| Independent reviewer and owner approval | NOT_RUN | Review or explicitly accepted exception under governance |
| External runtime/media/model benchmark | Not supplied | Required only before enabling such capabilities |

Do not turn a missing gate into PASS. A failed required gate blocks merge; NOT_RUN requires resolution or an explicitly accepted exception under [release governance](../release-and-client-upgrade-policy.md).

## Order of operations

Public PR review -> approved merge -> immutable tag and release notes -> private adoption branch pinned to tag and resolved SHA -> compatibility review -> private PR approval/merge. A staged private proposal may reference the exact candidate but must remain pending until the released target is verified. Do not label that proposal adopted or silently track main.

Rollback restores the prior reviewed pin and compatible private adaptations through a new PR, preserving evidence and publications. Branch cleanup must use ancestry or changed-file equivalence, confirm no open PR relies on the branch, and retain all unique work. Do not delete an active branch solely because its name looks old.
