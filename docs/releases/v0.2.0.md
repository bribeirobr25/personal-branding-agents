# Method 0.2.0: release scope, evidence and migration

This is a **prompt-first methodology release**, not an autonomous agent runtime, connector stack or proven business outcome. Publication is established only by the `v0.2.0` Git tag, its resolved commit and the published GitHub release. A document filename or a pending PR does not establish publication or private adoption.

## Included

Preserves the existing Creative Strategist work and progressive onboarding. Adds anchored concept selection, goals and five knowledge banks, native derivation, final-artifact approval, portable records, checkpoint/reuse templates, evaluation scenarios, optional-capability boundaries and an offline structural validator. All new examples are independently fictional. No client source exports, private strategy or account metrics are required by the public method.

Repository-only administration includes complete-checkout CI, one exact-head retired-branch cleanup and a tag/release workflow. These are maintenance tools for this repository, not general-purpose framework agents. Cleanup never targets main or the active development branch. Release automation never moves an existing tag or merges a PR.

## Compatibility and migration

- Stable task request/response envelopes remain. New domain records and canonical vocabulary require explicit adaptation.
- Normalize legacy `user-reported` to `user_reported` and content `draft` to `drafted`, recording migration.
- Legacy pre-draft PASS maps to SELECT eligibility, never owner approval; final gates keep PASS / REVISE / BLOCK.
- Preserve scheduled between approved and published, without inferring publication from elapsed time.
- Add concept_selected for new cycles, not retroactive gate results for old content.
- ApprovalRecord now requires `actor_role` and private `authority_ref` in addition to exact artifact/hash/action/destination. Unknown authority cannot authorize a new action; historical records are not rewritten as if new fields were originally present.
- Keep task/access/evidence/concept/content/action states distinct. Unknown restrictions/schemas fail safely.
- Preserve historical CSV rows and evidence. Old architecture/onboarding heading versions were document iterations, not release tags.

[Manual case ledger](../../tests/results/manual-text-2026-11-11.md) records one open-book, same-assistant text response for each of E01–E32 and L01–L08, plus explicit reruns and an owner-authority check. Initial E22 lacked a checkpoint and is retained as INPUT_LIMITED; E22-R2 uses a populated synthetic checkpoint. This is not an all-first-pass claim.

[Onboarding/content ledger](../../tests/results/onboarding-content-2026-11-11.md) records an invented multi-turn input, actual sequential-role outputs, three concepts, selection, a draft with calculated hash, five same-model review judgments and blocked invalid continuations. No real person, account, paid tool or public content was used.

Separately executed automated review examines supplied public source snapshots and these outputs. Its scope, findings and remediation are recorded in the PR; it is not a human audit, independent generation, legal opinion or security certification. The owner explicitly authorized completion of the repository work; private conversation/identity evidence is not copied into public notes. No review/test gate is silently waived.

| Gate | Evidence and scope |

| Scope/contracts/migration | Current documents, JSON and templates; owner-authority/exception ambiguities corrected before release |

| Runtime/media/offline/payment enforcement | NOT_IMPLEMENTED / NOT_TESTED; no activation or guarantee implied |

The scenario definitions retain initial NOT_RUN placeholders as reusable fixtures; current observations live in run ledgers. Do not mistake fixture defaults for missing run evidence or a recorded text response for enforced runtime behavior. Follow [release governance](../release-and-client-upgrade-policy.md); unresolved material failures block merge and owner approval cannot be waived.

## Adoption, rollback and maintenance

Reviewed public merge -> immutable-by-policy tag and release -> private adoption pinned to tag/full SHA -> compatibility review -> authorized private merge. A staged private proposal remains pending until the actual released target is verified. Git tag protection is not claimed merely because this process promises not to move a tag.

Rollback restores a prior reviewed pin and compatible private adaptations through a reviewed PR, preserving evidence and publications. Branch cleanup verifies unchanged heads, preserved work, protection and PR dependencies, and uses exact-head leases. The active branches remain available for continued work.
