# Investigation of historical R16/A/U2 timeout

Scope: `discovery-codex-pilot-v2-2026-11-12/R16-1-A-2`, starting from commit
`506a8f274293027e4db49cbb8b9766929c79a440`. Investigation is read-only with
respect to that historical run. No replay, resume, replacement answer or merge
with a subsequent run was performed. **Outcome remains UNKNOWN.**

## Observed evidence

- `transport.json`: one local CLI request, one attempted forward, return code 1,
  `TimeoutError`, elapsed 182.22347312502097 seconds.
- `dispatch.json`: OUTCOME_UNKNOWN before the network operation; this proves an
  attempt, not provider acceptance or generation completion.
- No `receipt.json`, `response.sse`, `response.json` or answer was recorded.
- The CLI thread ID is `01a1cd44-dd0a-7981-9b2f-01b4f246fc95`. It is a **local**
  ephemeral session ID. The saved outbound request has no client metadata,
  previous-response ID, conversation ID or thread ID; that local ID was not sent
  to the provider and cannot be represented as a remote response receipt.
- The original invocation's temporary runtime directory no longer exists. It was
  an ephemeral CLI run, so there is no saved local thread to reopen. No unrelated
  personal history or memory was searched.
- The installed app-server schema exposes local thread operations, not a
  `response/retrieve` method for this native transport. Account methods return
  allowance information, not per-request response recovery records.

## Recovery boundary

No provider response ID or HTTP request ID is available for a targeted lookup.
The official [app-server documentation](https://learn.chatgpt.com/docs/app-server)
describes reading persisted local threads, which does not recover this deleted,
ephemeral runtime or identify an unacknowledged remote request. The current
[ChatGPT-plan preview documentation](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)
also describes stateless HTTP inputs and no persistent conversation storage for
that flow. It describes the newer Sign-in-with-ChatGPT route, so it is supporting
context, not proof about internal retention on the exact native endpoint used here.

No documented provider-side lookup available to this adapter can be addressed with
the evidence retained. No broad account-history search, invented-ID request, paid
API probe, support message or new inference was used as a recovery attempt. Provider
internal logs may exist but are not accessible through the available interface.
We cannot prove that the provider never generated a response, nor recover its
text or token usage. Those values remain unknown.

## Probable cause and limits

The saved original code creates `response.sse` immediately after `opener.open`
returns. The absence of that file, combined with `TimeoutError` near the configured
180 seconds, places the observed stall **before successful HTTP-open/headers return**.
This supports a network or upstream-service wait as the likely failure class.
The old trace does not distinguish connection/TLS, request transmission, or waiting
for HTTP response headers. It does not establish a particular outage or a model
reasoning problem. The CLI's generic local 400 HTML is generated by the broker
after the timeout; it is **not an HTTP 400 received from the provider**.

The CLI's fallback-model-metadata warning also appears in successful calls and
does not establish the timeout's cause. Frozen instructions and model selection
were explicitly supplied in the actual outbound payload.

## Narrow remediation

The executor now records HTTP_OPEN/STREAM_READ/STREAM_EOF, elapsed time and bytes,
persists safe receipt headers immediately, and captures a response.created ID from
complete SSE lines while preserving the raw stream. Offline tests cover a timeout
before headers and after partial SSE, with exactly one network attempt. This
improves diagnosis; it does not claim to repair an unconfirmed provider fault.

Model, prompt bytes, endpoint, generation settings, resource thresholds, 180/210s
timeouts, isolation and zero-retry policy are unchanged. The owner's resumption
request authorizes a **fresh 12-call pilot**, preregistered separately. Historical
UNKNOWN is retained even if the new pilot later succeeds.
